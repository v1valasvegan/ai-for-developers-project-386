# Окошко

Учебный сервис записи на звонки по мотивам Cal.com: владелец публикует доступное время, гость выбирает свободный слот и бронирует встречу.

## Текущий этап и запуск

Локально реализованы информационная главная, пошаговое бронирование на `/book` (сначала тип или время), создание типов и список текущих/предстоящих встреч на `/owner`, файловая SQLite, `GET /api/health` и единая генерация API. Интерфейс использует сгенерированный SDK. Пересечения между любыми типами исключаются атомарно; повтор успешной попытки возвращает ту же запись. Бронирование принято и опубликовано в [v0.2.0](https://github.com/v1valasvegan/ai-for-developers-project-386/releases/tag/v0.2.0); Docker-упаковка относится к следующему этапу.

Словарь проекта — [GLOSSARY.md](GLOSSARY.md), принятые решения — [docs/adr/](docs/adr/). Единая [спецификация бронирования](https://github.com/v1valasvegan/ai-for-developers-project-386/issues/13) опубликована в GitHub; восемь согласованных вертикальных тикетов связаны с ней как подзадачи со встроенными зависимостями. Функциональные срезы прошли общее ревью, объединены в `main`, задачи №13–21 закрыты. Доказательства CI и выпуска записаны в [docs/releases.md](docs/releases.md).

Установите [mise](https://mise.jdx.dev/getting-started.html) и добавьте его в `PATH`. Версии инструментов закреплены в `mise.toml`, зависимости — в `package-lock.json` и `backend/Cargo.lock`.

```bash
mise trust
mise install
mise run install
mise run dev
```

- Фронтенд: <http://127.0.0.1:5173>.
- API: <http://127.0.0.1:3000/api/health>.
- Серверы работают под управлением pitchfork: `mise daemons status`, `mise daemons logs`, остановка — `mise run stop`.
- `mise run check` — все проверки, та же команда запускается в GitHub Actions на каждый push и еженедельно.
- `mise run test` — сборка, Vitest (RTL и реальный HTTP) и Playwright (desktop/mobile); `mise run lint` — Oxlint; `mise run fix` — форматирование.
- `mise run generate` — перегенерация OpenAPI, клиентского SDK и серверных типов/маршрутов.

Установка инструментов, первая загрузка генератора и проверки уязвимостей требуют сети. При занятых портах серверы сообщат ошибку, чужие процессы автоматически не завершаются. `vite preview` используется только для дымового теста, не для production.

## Сценарий владельца и гостя

Пошаговые маршруты, URL и состояния интерфейса описаны в [решении карты](https://github.com/v1valasvegan/ai-for-developers-project-386/issues/11#issuecomment-6796435760).

1. Единственный, заранее заданный владелец открывает страницу управления и создаёт тип встречи: «Знакомство», описание «Обсудим ваш проект», длительность — 30 минут.
2. Гость открывает публичную страницу без регистрации и выбирает, с чего начать: с типа встречи или даты и времени начала.
3. Если выбран тип, следующим шагом выбирает подходящее время в календаре ближайших 14 календарных дней. Если сначала выбрано время, выбирает подходящий ему тип. Предыдущий выбор на текущем шаге изменить нельзя: для этого нужно вернуться назад. Длительность слота соответствует выбранному типу встречи.
4. Вводит имя и email, подтверждает запись.
5. Сервис проверяет доступность и создаёт запись. Гость видит подтверждение с датой, временем и часовым поясом. Если время уже занято, сервис предлагает выбрать другой слот.
6. Владелец открывает список текущих и предстоящих встреч всех типов и видит новую запись с типом встречи, датой, временем и данными гостя. Текущие встречи отмечены «Идёт сейчас», завершившиеся не включаются в список. Пересекающиеся с ней интервалы больше нельзя забронировать.

## Обязательные функции и ограничения

- Один заранее заданный владелец; авторизации, личных кабинетов и регистрации нет. `/owner` технически доступен любому посетителю, включая данные гостей: это ограничение учебного проекта, не безопасное публичное администрирование.
- Тип встречи содержит уникальный читаемый код, название, описание и длительность.
- Окно записи — 14 календарных дней, сдвигающееся с течением времени.
- Длительность слота равна длительности выбранного типа встречи.
- Любые пересечения записей владельца запрещены, включая частичное наложение разных типов. Следующая встреча может начинаться ровно в момент окончания предыдущей.
- Проверка пересечений действует и для одновременно пришедших запросов: из двух конфликтующих записей создаётся только одна.
- Нет интеграций с внешними календарями и уведомлений. Занятость вне сервиса автоматически не учитывается.
- Отмена, перенос, оплата и встроенная видеосвязь не входят в базовый объём проекта.

## Время и расписание

Согласованное поведение:

- Владелец видит время в своём часовом поясе, гость — в своём. Пояс гостя определяется браузером, показан явно и доступен для изменения.
- Шаг доступных стартов — 15 минут независимо от длительности типа встречи: например, часовую встречу можно начать в 10:00, 10:15 или 10:30.
- Старт доступен, только если весь интервал встречи помещается в рабочие часы и не пересекается с существующими записями.

Расписание владельца:

- Часовой пояс — `Europe/Moscow` (московское время).
- Рабочие дни — понедельник–пятница, часы — 10:00–18:00.
- Окно записи — 14 календарных дней начиная с завтра по московскому времени: от 00:00 завтрашнего дня включительно до 00:00 дня через 15 дней от сегодня, не включая эту границу. Выходные входят в окно, но слотов на них нет.
- Окно сдвигается при наступлении нового дня в `Europe/Moscow`; отображение времени в поясе гостя не меняет его границы.

Экран выбора времени — три панели: информация о встрече и пояс, календарь с днями недели, время выбранного дня. На телефоне панели идут друг под другом. Занятые интервалы видны с пометкой «Занято», но не выбираются; полностью занятый день можно открыть для просмотра. Длительность занятого интервала соответствует настоящей записи, а не просматриваемому типу. Все границы приходят с сервера: браузер не вычисляет рабочий график и не получает список встреч с персональными данными.

## API и генерация

API бронирования описан в [спецификации](https://github.com/v1valasvegan/ai-for-developers-project-386/issues/13) и `api/main.tsp`:

- `GET /api/health` — работоспособность.
- `GET /api/meeting-types`, `POST /api/meeting-types` — каталог и создание типа.
- `GET /api/meeting-types/{id}/slots` — свободные интервалы и метаданные актуального окна; дополнительное поле `occupied` содержит занятые интервалы всех типов, пересекающие это окно, по возрастанию начала. Только `startsAt`/`endsAt`, без данных гостя, кода типа и идентификатора записи. `items` по-прежнему содержит только свободные слоты.
- `POST /api/bookings` — создание (`201`) или результат успешного повтора (`200`).
- `GET /api/bookings` — текущие и предстоящие встречи с серверными статусами.

Все списки возвращают `items`, включая пустой `200`; каталог сортируется по коду, интервалы и встречи — по началу. Создание возвращает сам ресурс. Ошибки содержат `code`, `message` и при необходимости `fieldErrors`: `400 validation_error`, `404 meeting_type_not_found`, `409 meeting_type_exists` / `slot_conflict` / `idempotency_key_reused`, `503 storage_unavailable`, `500 internal_error`, без внутренних подробностей.

- Бекенд — Rust + Axum, фронтенд — React + TypeScript + Vite + Mantine.
- `api/main.tsp` → TypeSpec OpenAPI emitter → `api/generated/openapi.yaml` (OpenAPI 3.0).
- `@hey-api/openapi-ts` генерирует TypeScript SDK с Fetch-клиентом в `frontend/src/api/generated/`.
- OpenAPI Generator `rust-axum` генерирует серверные типы и маршруты в `backend/generated/`. Реализация обработчиков — в `backend/src/`. Генератор имеет статус beta; совместимость проверяется настоящими HTTP/SDK и браузерными сценариями.
- OpenAPI Generator требует Java только для генерации: версия JDK, версия генератора и SHA-256 его JAR закреплены в `mise.toml`. JAR загружается из Maven Central и проверяется перед запуском.
- TypeScript закреплён на 6.0.3: используемый SDK-генератор несовместим с API компилятора TypeScript 7.
- Сгенерированные файлы не редактируются вручную: общая проверка повторяет генерацию и падает при расхождении.
- Коммиты — Conventional Commits; формат проверяется локальным хуком и в CI. Правила проверок и согласованные исключения описаны в [docs/quality-gates.md](docs/quality-gates.md).
- Dependabot еженедельно предлагает обновления npm, Cargo и GitHub Actions через PR без автоматического слияния. Конфигурация начнёт действовать после попадания в default branch; версии инструментов в `mise.toml` обновляются вручную.
- Release Please настроен для одного релиза приложения из `main`: предлагает версию и changelog в PR, а после разрешённого слияния выпускает тег и GitHub Release. Права, проверка CI bot-PR и ограничения описаны в [docs/releases.md](docs/releases.md). Автоматическое создание PR №23 и опубликованный v0.2.0 подтверждены настоящими успешными Actions; ссылки приведены в документации релизов.

## Хранение данных

Реализована файловая SQLite для типов, записей и успешных ключей попыток с одним экземпляром бэкенда. При запуске автоматически применяются `backend/migrations/001_meeting_types.sql` и `002_bookings.sql`, без демонстрационных данных. По умолчанию файл — `data/okoshko.sqlite3` относительно текущего каталога процесса; `data/` создаётся автоматически и исключён из Git. `DATABASE_PATH` задаёт другой путь; его родительский каталог должен существовать и быть доступен процессу для записи. Обычный перезапуск с тем же файлом сохраняет типы, записи и успешные ключи попыток. Запись и ключ сохраняются одной транзакцией с блокировкой записи до проверки занятости. Не удаляйте файл при пересборке или рестарте.

Используйте тот же постоянный том при пересоздании контейнера. Несколько экземпляров бэкенда не поддерживаются. Граница атомарного создания описана в [ADR](docs/adr/0003-sqlite-atomic-bookings.md). Том не равнозначен резервной копии: его удаление уничтожает данные.

## Docker и публичный деплой

**Публичный URL пока не опубликован; облачная приёмка ещё не выполнена.** Наличие Dockerfile не означает завершённый деплой. Не загружайте рабочую локальную БД в облако: `/owner` и список гостей публичны, для учебного сервиса допустимы только вымышленные данные.

### Локальный запуск образа

Корневой многостадийный `Dockerfile` собирает React и Linux release-бэкенд. Axum раздаёт SPA и `/api` с одного origin, без Vite/Node в runtime. SDK продолжает использовать origin страницы. Зависимости закреплены lockfile, базовые образы — digest; Docker не требует установленного на хосте Node, Rust или Java.

```bash
docker build -t okoshko:local .
docker volume create okoshko-data
docker run --rm --name okoshko \
  --mount type=volume,source=okoshko-data,target=/data \
  --env PORT=8080 --publish 8080:8080 okoshko:local
```

Приложение запускается автоматически: <http://localhost:8080>, здоровье — `/api/health`. Значение `PORT` (1–65535) выбирает адрес `0.0.0.0:PORT`; простого `EXPOSE` недостаточно. Без `PORT` нативный сервер сохраняет `BIND_ADDR`/`127.0.0.1:3000`; образ задаёт `PORT=3000`. `STATIC_DIR` указывает на собранную SPA, в образе это `/app/public`; `DATABASE_PATH=/data/okoshko.sqlite3`. Неверный порт или отсутствующий index при заданном `STATIC_DIR` препятствуют старту.

Обычный restart и пересоздание с тем же volume сохраняют типы, встречи и ключи успешных попыток. Без постоянного тома данные теряются при пересоздании контейнера; при удалении тома восстановление не гарантируется. Миграции выполняются при запуске, когда том уже доступен, а не при сборке. Образ по умолчанию работает от UID10001. Для root-owned volume Railway используется `RAILWAY_RUN_UID=0`: entrypoint меняет владельца только каталога `/data`, затем немедленно запускает сервер от UID10001. Это не разрешение серверу работать от root.

```bash
mise run docker:check
```

Проверка входит в `mise run check`: собирает образ, запускает его на PORT4100/4101, проходит настоящий браузерный сценарий и частичный конфликт60/30 минут, пересоздаёт свой контейнер с тем же томом и проверяет запись и идемпотентный повтор через SDK. Собственные контейнеры/том/тег удаляются в конце, чужие ресурсы не затрагиваются. Docker обязателен, тихого пропуска нет. На первом запуске нужны сеть и место для базовых образов.

### Подключение Railway MCP в Pi

Постоянный диск отсутствует на бесплатном Render, поэтому для SQLite выбран Railway с volume. Бесплатность зависит от доступных кредитов и лимитов аккаунта, не гарантируется навсегда. Trial заявляет $5 на срок до30 дней, Free — $1 кредита ежемесячно. При исчерпании квоты сервис может остановиться; действующие условия и срок хранения отключённого volume проверяйте в аккаунте. Платный Hobby или карту без отдельного согласия не подключать.

Установите официальный [Railway CLI](https://docs.railway.com/cli), проверенная версия —5.74.0. Вход на сайте не заменяет вход CLI:

```bash
railway login
railway whoami
# railway должен быть доступен в PATH процесса Pi
# Для нового конфига; существующий объедините, не затирая другие серверы.
test -e .pi/mcp.json || cp .pi/mcp.example.json .pi/mcp.json
```

В Pi подтвердите доверие проекту через `/trust`, затем выполните `/reload`. Проверка подключения — `pi mcp list` и read-only `whoami` через MCP. Шаблон использует официальный `railway mcp local`, инструменты которого умеют управлять сервисом, volume и доменом; обычный `railway mcp` подключается к hosted серверу с другим набором инструментов. Логин хранится в личном профиле CLI, не в Git. Активный `.pi/mcp.json`, `.railway/`, `.env` и личная конфигурация исключены из Git/контекста образа; безопасный `.pi/mcp.example.json` коммитится. Не передавайте токены в чат, build args или переменные приложения.

После разрешения агент через MCP проверяет аккаунт/квоту и создаёт один сервис, один volume `/data` и HTTPS-домен. Настройки сервиса задаются через MCP: корневой `Dockerfile` (автоопределяется при сборке), одна реплика, заданный хостингом `PORT`, `DATABASE_PATH=/data/okoshko.sqlite3`, `RAILWAY_RUN_UID=0`, healthcheck `/api/health` с timeout60 секунд, restart `ON_FAILURE` с максимум3 попытками. Том подключается отдельно. `railway.toml` не используется: Config as Code [снят с поддержки для новых сервисов](https://docs.railway.com/infrastructure-as-code#iac-vs-config-as-code), для прежних отключается01.12.2026. Новый IaC-стек ради одного сервиса не добавляется; проверяйте фактические настройки сервиса через MCP после создания. При загрузке через CLI/MCP используйте корень чистой проверенной рабочей копии или `git archive` вне неё. Корневой `.railwayignore` явно сохраняет закоммиченные `backend/generated` и SDK, но исключает личную конфигурацию, зависимости, сборки и БД: без явных разрешений generated-код терялся в облачном контексте. Не убирайте защитные исключения ради загрузки файлов. Дождитесь успешного deployment и реального браузерного сценария. Деплой исходников заново собирает образ: соответствие исходному SHA не означает совпадение digest с локальным image. Рестарт с томом сохраняет данные; удаление volume или его удаление хостингом после истечения тарифа — нет.

### Публичная приёмка

После публикации выполните с реальным origin, без вложенного пути:

```bash
BASE_URL=https://YOUR-SERVICE.up.railway.app \
  SMOKE_STATE_FILE=.cache/railway-smoke.json mise exec -- npm run test:deploy
# После разрешённого рестарта того же сервиса с тем же томом:
BASE_URL=https://YOUR-SERVICE.up.railway.app SMOKE_MODE=verify \
  SMOKE_STATE_FILE=.cache/railway-smoke.json mise exec -- npm run test:deploy
```

Это команды с шаблонным адресом, не свидетельство уже опубликованного сервиса. Первый прогон создаёт различимые синтетические типы/запись с email в example.com: гость выбирает тип и слот, видит подтверждение, владелец — встречу; вторая открытая форма получает понятный409, а частичное пересечение другого типа также отклоняется. Проверяются мобильный список, занятость и повтор того же ключа без дубля. Ответы API не подменяются; запросы выполняются SDK. Режим verify после рестарта проверяет прежние типы, запись и повтор по сохранённому ключу. Он не требует, чтобы старый слот остался в сдвигающемся окне доступности: идущая встреча ещё видна владельцу, завершённая уже исключается из его списка, но успешный replay по-прежнему подтверждает сохранность. Свежие409 и занятость календаря проверяются первым прогоном. Демозаписи остаются в сервисе; удаления через API нет. Test-state содержит только синтетическую попытку для проверки, не служит восстановлением пользовательской формы приложения.

Второй проект ради этой сдачи не создаётся. При продолжении переносите принятые исправления адресно и запишите в его README фактическую исходную версию/SHA первого проекта, не заменяя новые изменения целыми файлами.

## Проверки бронирования

Согласованы проверки интерфейса через React Testing Library и user-event, подробные HTTP-тесты настоящего сервера с SQLite и небольшой набор сквозных сценариев Playwright. Для тестов используются изолированные данные и управляемые часы; подробные сценарии и доказательства приёмки записаны в [решении карты](https://github.com/v1valasvegan/ai-for-developers-project-386/issues/12#issuecomment-6797352356).

Подключены RTL + user-event, настоящий HTTP/SQLite и небольшой Playwright-набор на desktop/mobile: оба порядка выбора от создания типа до списка владельца, «Назад», URL/F5, конфликт после выбора и повтор при потере настоящего ответа без дубля. HTTP проверяет валидацию, окно/смещения/полночь, пересечения/примыкание, параллельные запросы, идемпотентность, ошибки и перезапуск.

Каждый независимый тест создаёт временный файл SQLite в системном временном каталоге и убирает его вместе с процессами даже при неудаче; только сценарий перезапуска открывает тот же файл повторно. Рабочая база не используется. Подготовительные SQLite-фикстуры старых проверок не служат каналом проверки результатов: новые записи и единственность проверяются через API. Успешные ответы не подменяются; MSW применяется только для изолированных ошибок/сетевого сбоя. Управляемые часы сервера доступны лишь debug-сборке через внутренний файл `OKOSHKO_TEST_CLOCK_FILE`, без HTTP API; release-сборка использует настоящие часы.

Клиентские GET-запросы выполняются через TanStack Query и сгенерированный SDK. Кэш изолирован в памяти экземпляра приложения: каталог переиспользуется 30 секунд и инвалидируется после создания типа; слоты хранятся отдельно по коду типа и заново проверяются при открытии выбора/URL. Список владельца обновляется при возврате во вкладку/окно и раз в минуту, только когда вкладка встреч активна и страница видима; ошибка фонового обновления не стирает старый список. После успешной записи инвалидируются встречи и свободное время **всех** типов. Автоматические повторы отключены, при сетевой ошибке доступен явный повтор. Кэш не сохраняется в localStorage/sessionStorage.

Проверенная форма с выбранным временем не перепроверяется фоновыми GET во время ввода или неопределённой попытки: это сохраняет ошибки полей и возможность безопасного повтора после потери ответа. «Назад», новый выбор и F5 вновь проверяют доступность, а POST всегда окончательно проверяет занятость. Создание записи остаётся явным вызовом SDK вне mutation-кэша Query: персональный снимок и ключ попытки не попадают в его кэш.

Ключ попытки и снимок гостевых данных живут только в памяти открытой формы. После потери ответа повторите прежнюю попытку: запись могла сохраниться. F5 восстанавливает только тип/время из URL с проверкой доступности, но не личные данные, ключ или подтверждение. Сохранённая серверная запись при этом не отменяется.

Воспроизводимые команды (после `mise run install`):

```bash
mise run generate
mise run build
# Реальный API без демонстрационных данных; остановка — Ctrl+C
DATABASE_PATH=/absolute/existing/directory/catalogue.sqlite3 mise exec -- cargo run --locked --manifest-path backend/Cargo.toml
# В другом терминале
curl --fail-with-body http://127.0.0.1:3000/api/meeting-types
mise exec -- npx vitest run tests/catalogue.test.mjs frontend/src/Catalogue.test.jsx
mise exec -- npm run test:browser
mise run check
```

`mise run install` устанавливает Chromium и системные зависимости Playwright (в Linux могут потребоваться права sudo). `mise run check` включает все новые тесты и повторную генерацию; локальный успех не означает зелёный удалённый CI.

## Статус проверок Хекслета

Workflow Хекслета управляется учебной платформой и требует Actions-секрет `HEXLET_ID`. На push от Dependabot обычные Actions-секреты недоступны: для таких запусков `HEXLET_ID` должен быть отдельно настроен владельцем в Dependabot secrets, если это требуется платформой. Ошибка `Input required and not supplied: hexlet-id` возникает до проверки кода приложения.
