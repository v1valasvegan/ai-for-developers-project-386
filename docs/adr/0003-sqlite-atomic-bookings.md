# SQLite и атомарное создание записей

Для одного владельца выбираем SQLite и один экземпляр бэкенда: данные сохраняются после перезапуска без отдельного сервера БД. В Docker файл базы размещается в постоянном томе. Хранение только в памяти теряло бы записи, а PostgreSQL и распределённые механизмы добавили бы ненужную для этого масштаба инфраструктуру.

Один владелец не исключает одновременные запросы гостей. Проверка занятости и создание записи выполняются в одной транзакции с получением права записи до чтения занятости, чтобы два запроса не прошли проверку одновременно. Пересечения проверяются по всем типам встреч; примыкание разрешено. Уникальность нормализованного кода типа встречи и ключа попытки закрепляется ограничениями базы.

Ключ попытки сохраняется атомарно с записью: повтор с теми же данными возвращает её подтверждение, с другими — ошибку. На фронтенде ключ и снимок данных живут только в открытой форме; после перезагрузки попытка не восстанавливается. Это сознательно ограниченная защита от сетевых повторов, без истории попыток, отдельного API проверки и автоматического восстановления. Потеря состояния формы не отменяет серверную запись.

Подробные правила и примеры: [решение карты бронирования](https://github.com/v1valasvegan/ai-for-developers-project-386/issues/9#issuecomment-6794573160). Этот ADR фиксирует согласованную архитектуру; реализация относится к следующему этапу.
