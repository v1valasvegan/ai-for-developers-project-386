# Проверки каркаса

Основа: [Dev Quality Gates](https://github.com/mokevnin/dev-quality-gates), [инструкция внедрения](https://github.com/mokevnin/dev-quality-gates/blob/main/docs/adopt.md). Выбраны только подходящие к каркасу инструменты из Recommendations.

## Что проверяется

| Область                                | Инструмент                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------------- |
| Версии, задачи и процессы              | mise, hk, pitchfork                                                                     |
| Rust                                   | rustfmt, Clippy с `-D warnings`, cargo-machete                                          |
| TypeScript / React                     | Oxlint с `--deny-warnings`, oxfmt, строгий TypeScript, Knip                             |
| Запуск приложения                      | Vitest: реальный Rust-процесс, собранный фронтенд, запрос через SDK                     |
| API                                    | TypeSpec, vacuum с блокировкой предупреждений, повторная генерация OpenAPI / SDK / Axum |
| Секреты                                | Betterleaks: рабочие файлы и полная история всех Git refs, без live validation          |
| Уязвимости                             | cargo-deny для Rust, OSV-Scanner для npm lockfile                                       |
| Лицензии и источники Rust-зависимостей | cargo-deny                                                                              |
| GitHub Actions, shell-команды workflow | jactionlint, ShellCheck                                                                 |
| Conventional Commits                   | commitlint                                                                              |
| Инструкции агентам                     | agnix с `--strict`                                                                      |
| Обновления зависимостей                | Dependabot: npm workspaces, Cargo и GitHub Actions; конфигурацию проверяет jactionlint  |

## Когда запускаются

- Pre-commit: форматирование, быстрый линтер изменённых файлов, Rust-форматирование, поиск секретов в staged-содержимом. Проверки не исправляют файлы автоматически; hk временно сохраняет нестейдженные изменения, чтобы проверить содержимое коммита.
- Commit-msg: commitlint.
- Pre-push и CI: `mise run check`. CI срабатывает на каждый push во все ветки; результат push-проверки виден и в PR из этой ветки. Отдельного дублирующего PR-trigger нет.
- Еженедельно и вручную через workflow_dispatch: тот же полный прогон, включая внешние базы уязвимостей.

Хуки можно обойти, поэтому обязательная проверка — CI. Новые GitHub Actions закреплены полными SHA. Автоматические релизы ещё не подключены.

`.miserc.toml` исключает домашний `~/.tool-versions` из поиска конфигурации: проект задаёт свою полную цепочку инструментов и не должен устанавливать чужие глобальные Erlang/Elixir или другие asdf-tools. Домашний файл при этом не изменяется.

## Границы проверок и согласованные решения

- `api/generated/`, `frontend/src/api/generated/`, `backend/generated/` — вывод генераторов. Их стиль и зависимости шаблона не исправляются вручную. Они исключены из проверок форматирования и неиспользуемых зависимостей, но компилируются, проверяются на уязвимости, сканируются на секреты и сверяются повторной генерацией.
- `.github/workflows/hexlet-check.yml` и `.github/workflows/README.md` сохраняются без изменений. Линтер workflow запускается и для служебного workflow; форматтер не меняет управляемые Хекслетом файлы.
- Старые коммиты до `a91f02f4c54de15eb6a4fd9b431b33a630c1ae8c` предшествуют соглашению Conventional Commits. commitlint проверяет новые коммиты после этой точки; история не переписывается.
- Владелец согласовал MPL-2.0 только для транзитивных `cssparser@0.38.0` и `dtoa-short@0.3.5`, которые приходят через шаблон серверного генератора. Разрешения закреплены на эти версии в `backend/deny.toml`; при обновлении потребуется повторное рассмотрение. Другие MPL-зависимости автоматически не разрешаются.
- Разные транзитивные major-версии Rust-crates могут сосуществовать; политика не требует их искусственного объединения. Неизвестные registries, Git-источники и wildcard-зависимости запрещены.
- npm overrides обновляют транзитивные `js-yaml` и `undici` до исправленных совместимых версий. Уязвимости не подавляются.
- Baseline для ошибок приложения и исключения для уязвимостей не вводились.
- Knip проверяет корень и frontend как npm workspaces. `scripts/*.mjs` — отдельные точки входа CLI. Три зависимости `@typespec/http`, `@typespec/openapi`, `@typespec/openapi3` используются в `api/main.tsp` и `api/tspconfig.yaml`, которые Knip не анализирует; это явно отражено в `knip.jsonc`. `betterleaks` и `java` устанавливает mise. Только для `frontend/src/api/generated/**` исключены сообщения о неиспользуемых файлах, экспортах и типах; анализ зависимостей и разрешения импортов сохранён. Подсказки об устаревшей конфигурации Knip считаются ошибками.

## Что не подключено

- ESLint / Prettier не дублируют выбранные Oxlint / oxfmt.
- dependency-cruiser и собственные архитектурные правила отложены до появления модулей приложения; syncpack не нужен для одного frontend-пакета.
- Проверки CSS, браузерной доступности и размера бандла отложены до появления интерфейса; сейчас только заглушка.
- Нет базы, миграций, Dockerfile, Terraform или Kubernetes-манифестов — соответствующие проверки не устанавливаются.
- `check-jsonschema` пока не добавлен: используемые конфигурации проверяют сами инструменты; workflow проверяет jactionlint, OpenAPI — vacuum.
- Renovate не устанавливается: владелец выбрал встроенный Dependabot после блокировки установки Renovate 44.206.2 защитой mise (trust downgrade у транзитивного `@yarnpkg/libzip@3.2.2`). Защита не отключалась, исключение не добавлялось.
- Dependabot не обновляет инструменты в `mise.toml`, версию mise в параметрах workflow, Pkl-пакет hk и JAR генератора OpenAPI с его SHA-256. Эти согласованные версии пока обновляются вручную.
- Документационные линтеры, coverage-пороги и сравнение breaking changes API пока не нужны для одного smoke-теста и первоначального health-контракта.
- Из Under review ничего не установлено. В подборке нет утверждённого инструмента для YAML style, межмодульной архитектуры Rust и сканирования контейнерных образов; эти пробелы не заполнялись случайными инструментами.

## Обновления зависимостей

`.github/dependabot.yml` задаёт еженедельную проверку npm (корень вместе с frontend workspace), Cargo в `backend/` и GitHub Actions. Обычные обновления предлагаются не ранее чем через 7 дней после релиза; cooldown не задерживает security updates. Не более пяти открытых version-update PR на экосистему. TypeSpec, Mantine и React обновляются согласованными группами, сообщения коммитов используют `chore(deps):` / `chore(deps-dev):`. Major-обновления TypeScript отложены до совместимости SDK-генератора с новым API компилятора.

Из обычных обновлений исключены `backend/generated/**` и управляемый Хекслетом `.github/workflows/hexlet-check.yml`. Исключение не отключает проверки уязвимостей: cargo-deny и OSV-Scanner по-прежнему проверяют lockfiles, а повторная генерация обнаруживает ручные изменения вывода генератора. Для обновления генерируемого crate нужно обновить генератор, перегенерировать вывод и проверить контракт.

Автоматическое слияние не настроено. PR должны пройти `mise run check` и ручное рассмотрение. Конфигурацию Dependabot проверяет уже подключённый jactionlint, поэтому отдельный валидатор не нужен. Версионные обновления начнут работать после попадания конфигурации в default branch; при отключённом Dependabot в настройках организации потребуется разрешение администратора. Dependabot alerts и security updates включаются отдельно в настройках GitHub — файл конфигурации сам их не включает.

GitHub CI пока не запускался: изменения не закоммичены и не отправлены. После push нужно проверить результат workflow; локальный зелёный прогон не заменяет эту проверку.

Проверки внешних баз могут падать при недоступной сети или появлении новых advisories — это ошибка проверки, а не повод возвращать успешный код выхода.
