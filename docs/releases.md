# Релизы приложения

## Что настроено

[Release Please](https://github.com/googleapis/release-please-action) обслуживает **одно приложение «Окошко»**, а не независимо публикуемые npm/Cargo-пакеты. Workflow [release-please.yml](../.github/workflows/release-please.yml) запускается только на push в `main` — фактическую default/целевую ветку проекта. Временные `feat/booking-*` не выпускают релизы. Action закреплён полным SHA; обновления предлагает Dependabot.

В [конфигурации](../release-please-config.json) один корневой компонент `.` со стратегией `simple`, которая учитывает изменения во всём репозитории:

- `version.txt` — версия приложения; `.release-please-manifest.json` — состояние версии для Release Please. Начальные `0.1.0` — отправная точка, **не доказательство существования опубликованного релиза**.
- `CHANGELOG.md` — автоматически предлагаемые заметки об изменениях. До первого релизного PR файл содержит только заголовок и пояснение.
- Теги — `v<версия>`, например `v0.2.0`, без префиксов компонентов. GitHub Release имеет ту же версию и заметки из changelog; тег указывает на коммит слитого релизного PR.
- `package.json`, `frontend/package.json`, npm/Cargo lockfiles и `backend/Cargo.toml` не повышаются этой стратегией: это внутренние метаданные приватных частей приложения, не отдельные версии поставки. Версия API в TypeSpec и версии сгенерированных артефактов также независимы от версии приложения. Генерируемые файлы не редактируются ни вручную, ни релизным updater.

`bootstrap-sha` — `f3f28c049c6d199fcd6fce144713ca475d656be7`, точка перед первым сквозным каталогом (#14). Первый changelog собирается из последующих коммитов, без старой истории каркаса. После первого релиза Release Please использует предыдущий релиз как границу; bootstrap больше не действует.

## Жизненный цикл

1. Сопровождающий с отдельным разрешением отправляет и сливает функциональные изменения в `main` после обязательных проверок. Коммиты — Conventional Commits: `fix:` повышает patch, `feat:` — minor, `!` / `BREAKING CHANGE:` — major (включая переход с `0.x` на `1.0.0`). Например, после исходных `0.1.0` обычная новая функция предлагает `0.2.0`.
2. Push запускает Release Please: он создаёт или обновляет один релизный PR в `main` с предлагаемой версией, changelog, `version.txt` и manifest. Ручное повышение версии не является триггером. Только `docs:`, `chore:` или другие нерелизные изменения сами по себе могут не создать релизный PR. Обычные функциональные коммиты **не создают тег или Release**.
3. Сопровождающий проверяет PR: базовая ветка `main`, список изменений, SemVer и совпадение версий manifest/`version.txt`; в diff ожидаются только релизные метаданные. Не удаляйте служебные `autorelease: pending` / `autorelease: tagged` метки и структуру PR, по которым action распознаёт релиз.
4. До слияния нужны успешные обязательные проверки **для текущего head SHA релизного PR и правильной целевой ветки**, а не старый зелёный запуск. При обновлении PR проверка повторяется. Локальный `mise run check` полезен, но не заменяет удалённый CI.
5. **Только после отдельного разрешения на выпуск** сопровождающий сливает релизный PR. Следующий push в `main` запускает action, который создаёт соответствующие тег и опубликованный GitHub Release. Автоматического слияния, npm/crates-публикации, загрузки бинарных артефактов или развёртывания здесь нет.
6. Результат виден в Actions → Release Please, в слитом PR, в Tags и на странице Releases репозитория. Сверьте версию, тег, SHA слияния и release notes. Также проверьте Quality gates для фактически отправленного/слитого SHA в `main`; ожидающий запуск не считается зелёным.

## Права и CI

Используется только встроенный краткоживущий `GITHUB_TOKEN`, без нового PAT, секретов в файлах и дополнительных GitHub App:

- Вне релизной job — `contents: read`.
- В релизной job — `contents: write` (ветка, версия/changelog, тег и Release) и `pull-requests: write` (создание/обновление релизного PR и его lifecycle-меток). Остальные разрешения, в том числе `actions`, `packages`, `deployments`, `id-token` и отдельное `issues: write`, не выдаются. Права PR покрывают метки PR; работа с обычными задачами workflow не требуется.
- Владелец может быть обязан отдельно разрешить **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests**; создание релизной ветки/тега должно также допускаться действующими rulesets. Workflow не обходит защиту веток/тегов, не одобряет и не сливает PR. Настройки/права меняются только владельцем с разрешением, не этим файлом.

**Ограничение `GITHUB_TOKEN`:** созданные им PR и push в bot-ветку обычно не запускают новые workflow автоматически. Существующий Quality gates запускается на push, schedule и `workflow_dispatch`, без отдельного PR-trigger. Поэтому отсутствие CI у bot-PR не означает успех; не сливайте его без проверок и не отключайте обязательные checks.

После разрешения на удалённые действия запустите **Quality gates вручную через Run workflow с выбранной head-веткой релизного PR**, затем сверьте SHA запуска с head SHA PR (при необходимости через `gh run view`). Это использует существующий `workflow_dispatch` и тот же `mise run check`, а не сокращённую релизную проверку. Если обязательный workflow/правило репозитория не может быть удовлетворён таким запуском, остановитесь: владелец должен отдельно согласовать безопасную интеграцию токена GitHub App/PAT и её права/секрет, либо другой разрешённый способ запуска CI. Не обходите checks и не создавайте секрет без согласования. События тега/Release от `GITHUB_TOKEN` также не служат автоматическим триггером последующих workflow.

Управляемые Hexlet workflow и README не меняются. Его отдельные требования к секретам/обязательным проверкам остаются в силе. Release Please не добавлен в зависимости функциональных задач и не является условием запуска `mise run check`.

## Проверка и неподтверждённые части

Локально после установки зависимостей:

```bash
mise exec -- jactionlint
mise run check
```

Общий check включает синтаксис/безопасность Actions, форматирование, повторную генерацию и все функциональные тесты. JSON-конфигурацию также можно сверить с указанной в `$schema` схемой Release Please; её принятие схемой не доказывает поведение GitHub.

**Фактические релизный PR, его обновление следующим `feat:`/`fix:`, тег и GitHub Release пока не проверены на разрешённом запуске. CI для неотправленных изменений не подтверждён.** Для полной приёмки #15 нужны отдельные разрешения на push/слияние в целевую ветку, создание релизного PR и выпуск; при необходимости — действие владельца с настройками прав. Запишите ссылки на PR, Actions для точных SHA и Release после такого запуска. Не выпускайте проверочный релиз ради локальной приёмки и не закрывайте #15 только по наличию конфигурации. Эта внешняя проверка не блокирует независимую реализацию бронирования.
